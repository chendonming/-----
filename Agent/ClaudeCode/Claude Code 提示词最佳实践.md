# Claude Code 提示词最佳实践：让 AI 编程助手真正懂你

> **一句话总结**：给 Claude Code 的提示词，重点不是"指挥它每一步怎么做"，而是**说清目标、划清边界、备好上下文、约定验证方式**。
>
> 本文综合 Anthropic 官方文档 `Best practices for Claude Code`、`Memory`、`Skills` 三份资料整理，文末附参考来源。

很多人第一次用 Claude Code，会不自觉地带着和 ChatGPT 对话的习惯：一句话需求，等回复。结果发现 Claude Code 经常"自作主张"——改错了文件、动了不该动的代码、或者理解偏了方向。这通常不是 Claude 不够聪明，而是提示词的方式不对。

Claude Code 是一个 **agentic（自主）编程环境**，不是一个问答机器人。官方文档的原话是：

> "与回答完问题就等待的聊天机器人不同，Claude Code 可以读取你的文件、运行命令、做出修改，并在你观察、纠正或完全离开的情况下自主解决问题。"

这改变了工作方式：**不再是你写代码让 Claude 审查，而是你描述想要什么，Claude 负责探索、规划、实现。**

而理解下面这个核心约束，是写出好提示词的起点。

---

## 一、先理解最核心的约束：上下文窗口

官方文档明确指出：

> "大多数最佳实践都源于同一个约束：**Claude 的上下文窗口很快就会被占满，性能会随着它的填满而下降**。"

上下文窗口里装着你的整个对话：每条消息、Claude 读过的每个文件、每次命令的输出。一次调试会话或代码库探索，就可能产生几万 token。

当上下文接近满载时，Claude 可能"忘记"早先的指令，或者犯更多错误。**上下文窗口是最需要管理的资源。** 理解了这一点，你会发现后面所有建议都是它的推论：给更精准的上下文、别让无意义的探索浪费空间、及时清理会话、把重复内容固化到按需加载的文件里。

## 二、最重要的建议：给 Claude 一个能验证结果的方式

> **Tip（官方原文）**：给 Claude 一个可以运行的检查：测试、构建、或一张可对比的截图。这是"你在旁观看的会话"与"你可以放手离开的会话"之间的区别。

Claude 在"看起来做完"的时候就会停下。**如果不给它一个可以运行的检查，那么"看起来做完"就是它唯一的信号，你自己就成了验证循环**——每个错误都要等你发现。

这个检查可以是任何能返回"通过/失败"信号的东西：测试套件、构建退出码、linter、对输出做 diff 的脚本，或与设计稿对比的浏览器截图。

| 策略 | ❌ 之前 | ✅ 之后 |
|---|---|---|
| **提供验证标准** | "实现一个校验邮箱地址的函数" | "写一个 `validateEmail` 函数。示例用例：`user@example.com` 为 true，非法为 false，`user@.com` 为 false。实现后运行测试" |
| **可视化验证 UI** | "把仪表盘做得更好看" | "粘贴设计图，实现它。完成后截图与设计稿对比，列出差异并修复" |
| **处理根因而非症状** | "构建失败了" | "构建报这个错：粘贴报错。修复并验证构建成功。处理根因，不要抑制报错" |

更高阶的做法（取决于你投入多少精力）：

- **在一条提示里**：让 Claude 运行检查并在同一条消息里迭代，如上表。
- **跨会话**：把检查设为 [`/goal`](/docs/en/goal) 条件，独立评估器每轮后重查，Claude 持续工作直到条件成立。
- **确定性闸门**：用 [Stop hook](/docs/en/hooks#stop) 把检查写成脚本，未通过前阻止本轮结束。
- **第二意见**：用验证 [subagent](/docs/en/sub-agents) 或工作流，让一个全新模型尝试反驳结果——**干活的人不该给自己打分**。

还有一条贯穿始终的原则：**让 Claude 展示证据，而不是口头声称成功**——给出测试输出、它运行过的命令及返回结果、或结果截图。查看证据比重跑验证更快，也适用于你没盯着的会话。

## 三、先探索，再计划，后编码

> **Tip（官方原文）**：把调研、规划与实现分开，避免解决错误的问题。

让 Claude 直接跳去写代码，可能产出"解决了错误问题"的代码。官方推荐用 **plan mode（计划模式）** 把探索与执行分开，推荐的流程是四个阶段：

1. **Explore（探索）**——按 `Shift+Tab` 直到状态栏显示 `⏸ plan mode on`，或用 `claude --permission-mode plan` 启动。Claude 只读文件、回答问题，不做任何修改。
2. **Plan（计划）**——让 Claude 产出详细实现计划："我想加 Google OAuth。哪些文件要改？会话流程是什么？创建一份计划。"按 `Ctrl+G` 可在编辑器里直接改计划。
3. **Implement（实现）**——批准计划或 `Shift+Tab` 退出计划模式，让 Claude 按计划编码，并对照计划验证。
4. **Commit（提交）**——让 Claude 用描述性信息提交并开 PR。

同时官方也提醒：**计划模式也有额外开销**。修 typo、加一行日志、重命名变量这类范围清楚的小改动，直接让 Claude 做就好。**如果你能用一句话描述这个 diff，就跳过计划。**

## 四、在提示词里提供具体的上下文

> **Tip（官方原文）**：指令越精确，需要的纠正就越少。

Claude 能推断意图，但它不能读心。官方给出的四个策略：

| 策略 | ❌ 之前 | ✅ 之后 |
|---|---|---|
| **划定任务范围** | "给 foo.py 加测试" | "给 foo.py 写一个测试，覆盖用户登出这个边界场景。避免 mock" |
| **指向信息源** | "为什么 ExecutionFactory 的 API 这么怪？" | "翻一下 ExecutionFactory 的 git 历史，总结这个 API 是怎么演化成这样的" |
| **参考现有模式** | "加一个日历组件" | "看首页现有的组件是怎么实现的，理解其中模式。HotDogWidget.php 是个好例子。照这个模式实现一个新的日历组件……不用代码库里没用过的库" |
| **描述症状** | "修登录 bug" | "用户反馈会话超时后登录失败。检查 src/auth/ 里的认证流程，尤其是 token 刷新。先写一个能复现问题的失败测试，再修复" |

**模糊提示词也有用武之地**：当你正在探索、能承受纠偏成本时，像"这个文件你会怎么改进？"这样开放的问题，能抛出你没想到过的东西。

### 提供富内容

- 用 `@` 引用文件，而不是描述代码在哪——Claude 会在响应前先读它。
- 直接把图片粘贴 / 拖入提示词。
- 给文档和 API 参考的 URL。
- 用 `cat error.log | claude` 直接把数据管道传入。
- 或者干脆让 Claude 自己取：用 Bash 命令、MCP 工具、读文件去获取所需上下文。

## 五、沟通与迭代的技巧

### 像问资深工程师一样提问

用 Claude Code 学习陌生代码库时，直接问那些你会问同事的问题：日志是怎么工作的？怎么新建一个 API 端点？`foo.rs` 第 134 行的 `async move {}` 是做什么的？`CustomerOnboardingFlowImpl` 处理了哪些边界情况？**不需要特殊提示词，直接问。**

### 让 Claude 采访你

> **Tip（官方原文）**：对于较大的功能，先让 Claude 采访你。

用一个极简提示词开场，让 Claude 用 `AskUserQuestion` 工具采访你。它会问到技术实现、UI/UX、边界情况、权衡取舍——往往是你自己还没想到的硬骨头：

> "我想构建 \[简要描述]。用 AskUserQuestion 工具详细采访我。问技术实现、UI/UX、边界情况、顾虑和权衡。不要问显而易见的问题，深挖我可能没考虑到的难点。一直问到覆盖所有方面，然后写一份完整 spec 到 SPEC.md。"

**spec 写好后再开一个全新的会话去执行它**——干净的上下文专注于实现，你手里还有一份可参考的书面 spec。最有用的 spec 是自包含的：点明涉及的文件与接口、声明哪些不在范围内、并以一条端到端验证步骤结尾证明功能可用。

### 尽早、频繁地纠偏

最好的结果来自紧凑的反馈循环。用 `Esc` 中断 Claude（上下文保留，可以重定向）；用 `Esc + Esc` 或 `/rewind` 回滚；直接说"撤销那个"让 Claude 回退改动；用 `/clear` 在两个无关任务之间重置上下文。

**如果在同一个会话里就同一问题纠正了 Claude 两次以上，说明上下文已被失败尝试污染。`/clear` 后用吸收了教训、更具体的提示词重来**——干净会话 + 更好的提示词，几乎总是胜过带一堆累积纠偏的长会话。

### 主动管理上下文

- 任务之间频繁 `/clear`，重置上下文窗口。
- 接近上限时 Claude 会自动压缩，保留重要代码与决策。想控制压缩方向，用 `/compact <指令>`，例如 `/compact 关注 API 改动`。
- 快速小问题用 `/btw`——答案出现在可关闭的浮层里，**永不进入对话历史**，查细节不占上下文。
- 在 CLAUDE.md 里写压缩偏好，例如"压缩时始终保留修改文件清单和测试命令"。

### 用 subagent 做调研，保持主会话干净

既然上下文是根本约束，**subagent 是最有力的工具之一**。Claude 调研代码库要读大量文件，全部消耗你的上下文；subagent 在独立上下文窗口里探索，只汇报摘要：

> "用 subagent 调研我们的认证系统如何处理 token 刷新，以及是否有可复用的现有 OAuth 工具。"

实现完成后也可以用 subagent 验证："用 subagent 审查这段代码的边界情况。"——**一个带着全新上下文的审查者只看到 diff 和标准，而不是产出这个改动的推理过程**，因此能独立评估结果。CLAUDE Code 内置的 `/code-review` skill 就是用新 subagent 审查当前 diff 的 bug。

## 六、把好的提示词"固化"下来

Claude Code 有两套跨会话携带知识的机制，官方文档把它们区分得很清楚：

| | **CLAUDE.md 文件** | **自动记忆（auto memory）** |
|---|---|---|
| 谁写的 | 你 | Claude 自己 |
| 装什么 | 指令与规则 | 经验与模式 |
| 范围 | 项目 / 用户 / 组织 | 按仓库 |
| 何时加载 | 每次会话 | 每次会话（前 200 行或 25KB） |
| 用途 | 编码规范、工作流、项目架构 | 构建命令、调试洞见、发现的偏好 |

### CLAUDE.md：你写给 Claude 的持久指令

CLAUDE.md 是每个会话启动时都会被读到的特殊文件。官方建议：**先跑 `/init` 基于项目结构生成初版，再持续打磨**。

**何时往 CLAUDE.md 里加内容**（官方判据）：

- Claude 第二次犯同一个错误
- 代码评审抓到了 Claude 本应知道的项目常识
- 你又输入了一遍上一会话就输入过的纠正
- 一个新同事上手也需要同样的背景

**怎么写才有效**：目标 **每个文件 200 行以内**；用标题和列表组织；写具体到可验证的指令——"用 2 空格缩进"好于"格式规范点"，"提交前运行 `npm test`"好于"测试你的改动"；定期检查有没有互相矛盾的规则。

**精简判据（官方原话）**：对每一行问一句 *"删掉它，Claude 会犯错吗？"* 不会就删。**臃肿的 CLAUDE.md 会让 Claude 无视你的真正指令！**

| ✅ 放入 | ❌ 排除 |
|---|---|
| Claude 猜不出的 Bash 命令 | Claude 读代码就能推断出的东西 |
| 与默认不同的代码风格规则 | Claude 本就知道的标准语言约定 |
| 测试说明与偏好的测试运行器 | 详细 API 文档（给链接即可） |
| 仓库规范（分支命名、PR 约定） | 频繁变化的信息 |
| 本项目特定的架构决策 | 长篇讲解或教程 |
| 环境怪癖（必需的 env 变量） | 逐文件的代码库描述 |
| 常见坑与非显然的行为 | "写干净代码"这类不言自明的话 |

**位置与作用域**：`~/.claude/CLAUDE.md`（个人所有项目）、`./CLAUDE.md` 或 `./.claude/CLAUDE.md`（项目共享、入库）、`./CLAUDE.local.md`（个人项目内偏好，记得加进 `.gitignore`）。还支持 `@path` 语法导入其他文件，例如 `@README.md`、`@package.json`。用 `/context` 确认文件确实加载了，用 `/memory` 浏览和编辑。

### Skills：把重复流程固化成按需加载的技能

**官方定义技能的触发场景**：当你反复把同一份指令、清单或多步流程粘贴进对话；或者 CLAUDE.md 里某一段已经从"事实"长成了"流程"。

Skills 与 CLAUDE.md 的关键差异：**CLAUDE.md 每次会话都加载，而 skill 的正文只有被用到时才加载**，所以长参考材料在用到之前几乎零成本。存到 `.claude/skills/<name>/SKILL.md`（项目级）或 `~/.claude/skills/<name>/SKILL.md`（个人级）：

```markdown
---
name: api-conventions
description: 我们服务的 REST API 设计约定
---
# API 约定
- URL 路径用 kebab-case
- JSON 属性用 camelCase
- 列表接口始终带分页
- API 版本写在路径里（/v1/, /v2/）
```

- `description` 决定 Claude 何时自动加载它——把主要使用场景写在最前面。
- 想让只有你能手动触发（例如部署、提交这种有副作用的流程），加 `disable-model-invocation: true`。
- **注意**：官方文档指出，**自定义命令（slash commands）已并入 skills**——`.claude/commands/deploy.md` 和 `.claude/skills/deploy/SKILL.md` 都会生成 `/deploy` 且行为一致，但 skills 额外支持配套文件、调用控制、自动加载，推荐用 skills。
- skill 内还支持 `!` 命令注入动态上下文：例如 `` !`git diff HEAD` `` 会在 Claude 读取 skill 前先把命令输出替换进正文。

**一句话判据**：一件事你重复说了第二遍，就值得把它固化下来——写进 CLAUDE.md（常驻事实）或写成 skill（按需流程）。

## 七、避免常见失败模式

官方文档列出的高频错误及对策：

| 失败模式 | 表现 | 对策 |
|---|---|---|
| **厨房水槽会话** | 一个任务做到一半又插入无关问题，上下文全是无关信息 | 无关任务之间 `/clear` |
| **反复纠正** | 错了纠正、再错再纠正，上下文被失败尝试污染 | 两次纠正无效就 `/clear`，把教训写进更好的初始提示词 |
| **过度膨胀的 CLAUDE.md** | 太长导致 Claude 忽略一半，重要规则淹没在噪音里 | 无情精简；能删就删，或转成 hook 强制 |
| **信任而未见证** | Claude 产出了看起来合理但不处理边界情况的实现 | 始终提供验证（测试、脚本、截图）；无法验证就别发布 |
| **无限探索** | 让 Claude "调研一下"却不限定范围，读了上百个文件 | 收敛调研范围，或用 subagent 免得污染主上下文 |

## 八、最后：培养直觉

官方文档的收尾也很重要：**以上模式不是金科玉律**。有时你*应该*让上下文积累（正深陷一个复杂问题，历史很有价值）；有时*应该*跳过计划（任务是探索性的）；有时一个模糊提示词*恰恰正确*（你想先看 Claude 怎么理解问题再约束它）。

注意什么有效：当 Claude 产出好结果，留意你做了什么——提示词结构、给的上下文、所在模式；当它挣扎，问为什么——上下文太吵？提示词太模糊？任务对单次会话来说太大？

**你会逐渐发展出任何指南都无法概括的直觉**：何时具体、何时开放，何时计划、何时探索，何时清空上下文、何时让它积累。

## 速查清单

- [ ] 目标具体，含可验证的"完成标准"
- [ ] 给 Claude 一个能运行通过的检查（测试 / 构建 / 截图对比）
- [ ] 任务范围清楚（哪些文件、哪种场景）
- [ ] 上下文充分（文件路径 / 报错 / 环境 / 现有模式）
- [ ] 复杂任务先探索、后计划、再编码
- [ ] 一次只做一件事，任务之间 `/clear`
- [ ] 让 Claude 展示证据，而非口头声称成功
- [ ] 好提示词固化到 CLAUDE.md（常驻）或 Skills（按需）
